1. 二进制文件的结构

可执行文件不是"一段机器码"，而是有格式的容器。macOS 用 Mach-O，Linux 用 ELF，两者概念相同但字段不同。

Mach-O（macOS ARM64）

File Offset / VA 区域 大小
0x000 – 0x??? Mach-O Header + Load Commands（描述文件布局的元数据） ~500 B
VA 0x0 – 0x1_0000_0000 __PAGEZERO（仅虚拟，不占文件空间，捕获 null 解引用） 4 GB
file 0x0, VA 0x1_0000_0000 __TEXT 段（r-x，可执行，filesize = 0x4000） 16 KB
file 0x360, VA 0x1_0000_0360 __text（实际机器码，9 条指令） 36 B
file 0x384, VA 0x1_0000_0384 __unwind_info（栈展开元数据，C++ 异常 / crash reporter 用） 88 B
file 0x3dc – 0x4000 ★ CODE CAVE：页对齐填充（全 0x00，是可执行内存！） 15 KB
file 0x4000 __LINKEDIT（符号表、dyld 导出表、重定位信息，不可执行） 456 B

ELF（Linux x86-64）

File Offset / VA 区域 大小
0x0 ELF Header（64B）+ Program Headers（每个 56B） ~400 B
VA 0x401000（典型） .text（r-x，实际代码） varies
紧随 .text .rodata、.eh_frame、.eh_frame_hdr（只读数据 / 展开信息） varies
section 间隙 ★ Code Cave：节间对齐填充（通常 0x00，大小 = 页大小 mod） 0–4095 B
file 末尾 .symtab、.strtab、.debug_*（Section Headers 索引） varies
关键差异：Segment vs Section Mach-O 和 ELF 都有"段（segment）"和"节（section）"两层概念。
段：运行时概念，OS loader 按段映射内存（有权限 r/w/x）。
节：链接时概念，段内的细分区域（__text、.bss 等）。
Cave 通常藏在同一个"可执行段"内的节间隙或尾部填充中。

2. 为什么 Cave 一定存在

Cave 的根本来源是 页对齐（Page Alignment）。OS 内存管理以页为单位（macOS ARM64 通常 16 KB，Linux x86-64 通常 4 KB），所以每个可执行段的文件大小必须对齐到页边界。

# 我们的 main 二进制
实际代码:     36 bytes   (__text)
unwind_info:  88 bytes   (__unwind_info)
─────────────────────────
实际内容:    124 bytes
__TEXT 段:  16384 bytes  (= 4 KB 页，macOS 最小分配单位)
═════════════════════════
Cave 大小:  15396 bytes = ~15 KB   ← 全是 0x00，且在可执行段内！
结论 只要程序比一整页小，Cave 就必然存在。哪怕是大型程序，节与节之间也有对齐填充。 Cave 的字节是 0x00，它们在可执行内存中——只要你的代码能跳过去，CPU 就能执行它们。

3. udf #0x0 和 <unknown> 是什么

LLDB 对 __text 以外的区域强行按指令解码会得到这些输出：

输出原始字节真实含义
udf #0x0 00 00 00 00 ARM64 编码 0x00000000 = "Undefined" 指令。这是 __unwind_info / padding 的 0x00 字节被误当指令解码。
udf #0x3 03 00 00 00 __unwind_info 里的版本号字段（小端 int = 3），被误读为 ARM64 指令。
<unknown> 非 0x00 字节 __unwind_info 的实际元数据（函数地址、帧信息等），不是合法 ARM64 指令，解码器不认识。
注意 Cave 不能放在 __unwind_info 里！那里是 C++/ObjC 栈展开元数据，破坏它会导致 crash reporter、C++ 异常、backtrace() 失效。Cave 要放在 所有 section 结束之后 的纯 padding 区域（本例是 0x3dc 以后）。

4. Code Caving 原理

两种 patch 方式对比

方式原理限制适用场景
原地 Patch 直接覆盖原指令字节 只能用原指令的字节数 新逻辑 ≤ 原指令大小
Code Caving 原地写跳转，逻辑写到 Cave 需要找到可执行 Cave 新逻辑比原指令大，或逻辑复杂

执行流程图（本例）

原始代码：
  +12: ldr x8, [sp, #0x10]   ← 加载指针
  +16: ldr w8, [x8]           ← 解引用（可能崩）
  +20: str w8, [sp, #0xc]
  +24: ldr w0, [sp, #0xc]
  +28: add sp, sp, #0x20
  +32: ret

Patch 后：
  +12: ldr x8, [sp, #0x10]   ← 不动
  +16: b   cave             ← 4字节跳转（原 ldr w8,[x8] 的位置）
  +20: str w8, [sp, #0xc]   ← 不动，cave 跳回这里
  +24: ldr w0, [sp, #0xc]   ← 不动
  ...

Cave（在 padding 区 0x3dc）：
  cave+0: cbz x8, #8      ← x8==null? 跳过解引用
  cave+4: ldr w8, [x8]   ← 解引用（只有非 null 才到这）
  cave+8: b   +20         ← 跳回 str w8,[sp,#0xc]

  null  路径: cbz → cave+8 → b +20 → w8=0 → str 0 → ldr w0=0 ✓
  非null路径: ldr w8,[x8] → cave+8 → b +20 → str *x8 → ldr w0=*x8 ✓

B 指令编码（ARM64）

B 格式：  [ 000101 | imm26 ]   (32 bit, little-endian)
           bits[31:26] = 0x05
           imm26 = (target_VA - branch_VA) / 4   （有符号，±128 MiB 范围）

Python：
def encode_b(from_off, to_off):
    imm26 = (to_off - from_off) // 4
    assert -(1 << 25) <= imm26 < (1 << 25)     # 26-bit 有符号范围
    return struct.pack("<I", 0x14000000 | (imm26 & 0x3FFFFFF))

同段内 file-offset 差 = VA 差，可以直接用文件偏移计算。

# → 得到 __unwind_info: fileoff=900(0x384), size=88(0x58)
# → 得到 __TEXT filesize=16384(0x4000)
# Cave 安全区 = 所有 section 结束后到 segment 末尾

Step 2：定位 patch 点

xcrun llvm-objdump -d main
# 找到目标指令，记录 VA（如 0x100000370）
# VA → file offset: offset = VA - 0x100000000（简单二进制通常如此）

Step 3：获取字节码

# 汇编 → 字节码
echo "cbz x8, #8
ldr w8, [x8]
b #-0x6c" | xcrun llvm-mc -arch=aarch64 -show-encoding

# 字节码 → 反汇编（验证）
python3 -c "
import struct
word = struct.unpack('<I', bytes.fromhex('edffff17'))[0]
imm26 = word & 0x3FFFFFF
if imm26 >= (1<<25): imm26 -= (1<<26)
print(f'B target: current_VA + {imm26*4}')
"

Step 4：patch 脚本模板

import struct

with open("binary", "rb") as f:
    data = bytearray(f.read())

# 1. 定位 hook 点
hook_offset = data.find(b'\x08\x01\x40\xb9')

# 2. 找 Cave（在所有 section 结束后的 padding）
SAFE_START = 0x3dc    # ← 从 otool 得到，必须在所有 section 之后
cave_offset = None
for i in range(SAFE_START, len(data) - 12):
    if i % 4 == 0 and all(b == 0 for b in data[i:i+12]):
        cave_offset = i; break

# 3. B 指令编码
def encode_b(from_off, to_off):
    imm26 = (to_off - from_off) // 4
    assert -(1 << 25) <= imm26 < (1 << 25)
    return struct.pack("<I", 0x14000000 | (imm26 & 0x3FFFFFF))

# 4. 写 Cave 代码
data[cave_offset:cave_offset+12] = (
    b'\x48\x00\x00\xb4'                    # cbz x8, #8
    + b'\x08\x01\x40\xb9'                  # ldr w8, [x8]
    + encode_b(cave_offset+8, hook_offset+4)  # B back
)

# 5. Hook：原位置写 B cave
data[hook_offset:hook_offset+4] = encode_b(hook_offset, cave_offset)

with open("binary_patched", "wb") as f:
    f.write(data)

Step 5：验证

# 反汇编确认 hook 点
xcrun llvm-objdump -d --start-address=0x100000370 --stop-address=0x100000380 binary_patched
# 应看到: 1400001b   b 0x1000003dc

# 运行验证
./binary_patched; echo "exit: $?"

# LLDB 单步
lldb ./binary_patched
(lldb) b main
(lldb) r
(lldb) si   # step instruction

Step 4：x86-64 相对跳转编码

# x86-64 near jump: E9 + rel32 (4字节有符号偏移)
# rel32 = target - (jmp_addr + 5)   ← 5 = JMP 指令自身长度

def encode_jmp(from_off, to_off):
    rel32 = to_off - (from_off + 5)   # x86 偏移从指令末尾算起
    return b'\xe9' + struct.pack("<i", rel32)

# 注意：ARM64 的 B 从指令开头算，x86 JMP 从指令结尾算！

# 短跳转（±127 字节）：EB + rel8（2字节）
# 条件跳转：74(JZ) / 75(JNZ) + rel8，或 0F 84(JZ) + rel32

Step 5：x86-64 null 检查 cave 代码

# 原始 x86-64 指令示例：
# mov eax, [rax]   →  8B 00
# 要在前面插 null 检查

# Cave 代码（null check + dereference）：
from pwn import *
context.arch = 'amd64'

cave_code = asm("""
  test rax, rax          ; null check
  jz skip                ; if null, skip
  mov eax, [rax]         ; dereference
  skip:
  jmp 0x12345678         ; B back（地址需替换）
""")

# Linux x86-64 Cave 查找：找 .text 末尾的 CC/00 padding
text_section = elf.get_section_by_name('.text')
text_end = text_section['sh_offset'] + text_section['sh_size']
# 从 text_end 开始找 0x00 / 0xCC 区域

8. 避坑备忘

不能把 Cave 放在 __unwind_info 里 __unwind_info（macOS）/ .eh_frame（Linux）是栈展开元数据，破坏它会让 C++ 异常、crash reporter、backtrace() 出错。Cave 必须在所有 section 的 fileoff+size 之后的纯 padding 区域。
ARM64：cbz x8 vs cbz w8 指针是 64-bit，null check 应该用 cbz x8（\x48\x00\x00\xb4），而不是 cbz w8（\x48\x00\x00\x34）。虽然 null == 0 在低 32 位也成立，但语义上应匹配寄存器宽度。
x86-64：JMP 偏移从指令末尾算 JMP rel32 的偏移 = target - (jmp_addr + 5)，不是从指令开头。ARM64 的 B 是从指令开头。两个平台不同，不要混淆。
验证字节码的正确姿势
  1. 汇编 → 字节码：llvm-mc -show-encoding / nasm -f bin + xxd
  2. 字节码 → 反汇编：struct.unpack 手动解码 imm 字段，比较 target VA
  3. 最终用 llvm-objdump / objdump 确认 patched 二进制
macOS code sign / codesign 问题 修改二进制后原有签名失效，运行前需要重签：
codesign -s - --force main_patched（用本地 ad-hoc 签名）
如果是系统程序还需要关闭 SIP。自己编译的二进制无需此步。
